# wk

Статический Go CLI для проекта, связанного с wikisvc. Реализация
задач 02, 06 и 07A из `../backend/todo/` в отдельном Git-репозитории.
Серверная часть реестра шаблонов находится в соседнем `../backend`.

## Сборка и разработка

```sh
nix develop
nix develop -c just lint
nix develop -c just test
nix build .#wk
nix run .#wk -- --help
nix flake check
```

`flake.lock` фиксирует тот же nixpkgs, что и backend. Используется Go 1.26,
`buildGoModule`, `CGO_ENABLED=0`; единственная зависимость приложения —
`gopkg.in/yaml.v3 v3.0.1`. `gopkg.in/check.v1` в `go.sum` — транзитивная
тестовая зависимость yaml.v3, в бинарь не включается. `git` нужен при `init`
и `doctor`. Имя установленного бинаря задаётся один раз в `package.nix`.
Сборка запускает форматирование, `go vet ./...` и тесты всех пакетов с покрытием.
Порог покрытия каждой Go-функции — 100%; понижение ломает `just test` и сборку.

Начало работы:

```sh
nix run .#wk -- init --dir ../orders-platform \
  --url http://127.0.0.1:8787 --profile go-service
cd ../orders-platform
nix develop path:. -c wk doctor --json
```

Сразу после `init` файлы ещё не добавлены в Git: `path:.` позволяет Nix увидеть
их без staging. После самостоятельного `git add` flake-файлов можно использовать
обычный `nix develop`. CLI выполняет только `git init` и `git status`; выбор
файлов для staging и коммита остаётся человеку.

`--url` или `WIKI_URL` используется только для первоначального `init`.
Для обычных команд все параметры берутся из `.wiki-project.yaml` текущего каталога.
Имя проекта по умолчанию — имя целевого каталога; можно задать `--project`.
Без шаблона требуется `--profile`, с шаблоном профиль и scopes берутся из него.
`--scopes lang:go,app:orders` задаёт scopes при инициализации.

Собранный Nix-пакет записывает в новый `flake.nix` ссылку на свой неизменяемый
исходник в Nix store. Для распространяемого репозитория задай
`--wk-flake git+https://host/team/wk` либо `WK_FLAKE`: полученный flake можно
зафиксировать обычным `nix flake lock`. При запуске через `go run` этот параметр
нужен явно, например `--wk-flake path:/home/BadRabbit/work/wk`.

## Команды

Все команды поддерживают `--json`: один JSON-документ на stdout, диагностика на
stderr. Текстовые значения и ответы сервера очищаются от значения `WIKI_TOKEN`.

| Команда | Назначение |
|---|---|
| `init [--profile ID] [--template ID] [--dir DIR]` | docs-kit, серверный блок политик, манифест, git, flake с devShell, gitignore |
| `init --existing` | Только `docs/`, `AGENTS.md`, манифест; остальной проект сохраняется |
| `init --force --existing` | Явное разрешение перезаписать конфликтующие файлы |
| `init --offline --template ID` | Проверенный локальный кэш; политический блок помечается как ещё не загруженный |
| `doctor` | Упорядоченные `ok`/`warn`/`fail`: манифест, health, whoami, профиль, scopes, политики, MCP, агент, docs, git |
| `component add NAME [--lang LANG-id] [--kind svc\|lib] [--with-ai]` | Копия локального `_template`, draft, ID/owner, строка INDEX; дубликаты запрещены |
| `docs check [--docs DIR] [--code DIR] [--strict] [--no-registry]` | Встроенная проверка документации и генерация реестра ID |
| `docs upgrade` | Удаление старого `docs/_meta/check.py` |
| `check [--strict]` | Документация и актуальность блока политик |
| `policy sync` / `policy check` | Атомарное обновление блока / сравнение серверной версии |
| `policy search QUERY` / `policy show RULE-ID` | Чтение правил вики |
| `template list` / `template show ID` | Реестр и канонический YAML шаблона с digest |
| `propose --file PAGE.md [--title TITLE] [--kind manual]` | Создать черновик, загрузить страницу, проверить, отправить на ревью |

Обычный успех — код 0, ошибка — 1. `doctor` возвращает 0 при `ok`/`warn` и 1
при любом `fail`. Отсутствующие MCP и агент — предупреждения. `whoami` при 401
сообщает, что анонимный доступ выключен; reader получает предупреждение.

Повторный `init` с валидным манифестом без `--force` ничего не меняет, включая
mtime. `--force` не отменяет требование `--existing` для непустого каталога.
Все пути и конфликты проверяются до записи проектных файлов. Манифест пишется
последним. Каждый файл заменяется атомарно; общей транзакции для нескольких
файлов нет — при отказе диска возможны уже записанные файлы без манифеста.
Существующий Git-репозиторий, включая worktree или родительский репозиторий,
сохраняется. `wk` не делает коммитов и не запускает Git hooks.

`propose` получает `page_id` из YAML frontmatter Markdown-файла и передаёт
полный файл как JSON-строку, как требует текущий API wikisvc. При ошибках
валидации `submit` не вызывается; вывод содержит pid и ошибки. При сетевом
сбое после создания черновика pid остаётся в диагностике для ручного продолжения.

## Манифест

```yaml
version: 1
project: orders-platform
wiki:
  url: http://127.0.0.1:8787
  profile: go-service
  scopes: [lang:go, app:orders]
policy_blocks:
  - file: AGENTS.md
    profile: go-service
    scopes: []
    budget_tokens: null
    enforced: keep_must
template:
  id: ""
  digest: ""
docs:
  root: docs
```

`project`: `[a-z0-9][a-z0-9-]{0,63}`; `version` строго 1. `wiki.url` — origin
http/https без завершающего `/`, пути, query, fragment и userinfo.
`docs.root` и `policy_blocks[].file` — относительные пути внутри проекта без
`..`, `.git`, абсолютных путей и симлинков. Неизвестные поля на любом уровне,
повторные ключи, несколько YAML-документов, aliases и merge keys запрещены.
Ключи, содержащие `token`, `secret`, `password` без учёта регистра, запрещены
на любом уровне, кроме типизированного `policy_blocks[].budget_tokens` (числовой
бюджет, 1–100000). Токен не является частью манифеста.

По умолчанию HTTP-запросы анонимные, без `Authorization`. Необязательный
`WIKI_TOKEN` берётся только из окружения и используется как Bearer. В файл,
аргументы дочернего git, stdout/stderr он не записывается. Перенаправления
не выполняются, ответы ошибки не печатаются целиком. Ответ шаблона или
политик, содержащий этот credential, запрещено сохранять. Команд `login`,
`accept`, `promote`, `deprecate`, `revert` нет. Клиент не меняет права сервера;
анонимный доступ зависит от внедрения задачи 09 на сервере.

## Шаблоны

Администратор вики хранит их в `schema/project-templates/<id>.yaml`:

```yaml
id: go-service
title: Go HTTP-сервис
profile: go-service
scopes: [lang:go, app:service]
components:
  - {name: api, kind: svc, lang: LANG-go}
files:
  - path: main.go
    content: |
      package main
      func main() {}
policy_blocks:
  - {file: AGENTS.md, profile: go-service}
```

Доставка: `GET /api/v1/schema` → `project_templates`,
`GET /api/v1/schema/project-templates/{id}` → JSON-объект шаблона.
Сервер проверяет существование профилей и scopes при загрузке реестра.
Неизвестный шаблон — `E_TEMPLATE_UNKNOWN`/404; неверная схема, лимиты или
ссылки на реестр — `E_TEMPLATE_INVALID`. Обновление шаблонов требует
перезагрузки серверного реестра/перезапуска сервиса. Через proposals шаблоны
не изменяются: существующая граница записи только в `wiki/` сохранена.

Обе стороны запрещают неизвестные поля, включая `post_init`, `exec`, `script`,
`command`; пути в `.git`, выход из проекта, дубликаты и конфликт файла с
каталогом. Максимум 200 файлов, 256 КиБ на файл, 2 МиБ суммарного UTF-8 текста.
Клиент также отвергает симлинки на любом существующем участке пути,
не создаёт их и не перезаписывает. Запись через `os.Root` остаётся в каталоге
проекта при перемещении каталогов. Файлы сохраняются как обычные данные,
с правами 0644, ничего из шаблона не исполняется.

Скелет docs-kit встроен в бинарь. Файлы удалённого шаблона дополняют его;
уже существующие файлы проекта требуют `--force`. Канонизация — YAML
типизированной структуры в фиксированном порядке полей; комментарии и
порядок входных ключей не влияют на SHA-256. Порядок массивов сохраняется.
Digest включает весь шаблон, даже когда `--existing` применяет лишь docs.

Кэш: `$XDG_CACHE_HOME/wk/templates/<id>-<64 hex SHA-256>.yaml`, либо стандартный
пользовательский cache directory. `--offline` проверяет ID и digest содержимого;
при обновлении существующего проекта использует digest из манифеста,
при первичном init выбирает самый новый файл (при равном mtime — по имени).
Повреждённый кэш приводит к ошибке, сеть автоматически не используется.

Только явный `init --template github:owner/repo#id` читает
`https://raw.githubusercontent.com/owner/repo/HEAD/schema/project-templates/id.yaml`.
Туда не передаётся `WIKI_TOKEN`. После первого чтения применяются те же
валидация, канонизация и кэширование.

## Документация и политики

`wk docs check` работает локально. Требует манифест, читает корень из `docs.root`,
генерирует `_meta/registry.md`; `--no-registry` запрещает только запись реестра.
Код 0 означает отсутствие ошибок, 1 — ошибки (или предупреждения при `--strict`),
2 — неверные аргументы, 3 — отсутствующий манифест или каталог docs.
`wk docs upgrade` удаляет старый Python checker. Новые проекты его не получают.
Заголовок реестра сохранён побайтно для совместимости с эталоном; Python не вызывается.

`wk policy sync` получает готовый блок от сервера и атомарно заменяет единственный
блок в каждом файле. Повреждённые и неоднозначные блоки не перезаписываются.
`sync`, `check` и online `init` отправляют одинаковые параметры: профиль,
непустые scopes, числовой бюджет, непустой `enforced`. Пустые scopes и null-бюджет
оставляют значения профиля; допустимы `keep_must`, `all`, `none`.
`policy check` даёт 1 при устаревшем/отсутствующем блоке, 3 при недоступной сети.
Превышение серверного бюджета — предупреждение с количеством токенов.
`wk check --strict` объединяет проверку docs и свежести политик.

Ссылки `rule-*` разрешены только на политики из локальных сгенерированных блоков.
Определения этих ID в проектной документации запрещены. Реестр дополняется
секцией «Политики компании» с уровнем и профилем каждой политики.

Смысловая сверка документации запускается из UI backend задачей `docs_audit`;
команды `wk audit` нет. Хуки и skills (03/04) реализуются отдельно.

## Проверки и инструменты

Тесты используют стандартный `testing`, `httptest`, временные каталоги и
настоящий git. Проверяются все команды, JSON/коды выхода, утечки токена,
последовательность proposal-запросов, строгий YAML, traversal/симлинки,
ограничения шаблонов, стабильный digest, повреждённый кэш, offline,
идемпотентность и отказы чтения/записи. Покрытие учитывает все пакеты, включая
точку входа, без исключения production-файлов. Контролируемые отказы
файловой системы проверяют cleanup и запрет завершать init после ошибок записи.

Golden-тесты сравнивают stdout, exit code и реестр с замороженным Python oracle
на семи сценариях. Блок политик сравнивается с настоящим `wikisvc export_block`.
Эталоны в `testdata/`; скрипты регенерации в `scripts/` запускаются только при разработке.

При разработке использованы context7 (yaml decoder, Nix buildGoModule, Pydantic) и
graphify в корне этого репозитория:

```sh
nix develop -c graphify extract . --code-only --no-cluster
nix develop -c graphify query 'parseTemplate safePath atomicWrite'
```

`graphify` — внешний установленный инструмент разработки, не зависимость CLI.
Локальный `graphify-out/` исключён из Git и сборки.
