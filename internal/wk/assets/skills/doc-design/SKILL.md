# Проектирование задачи в документации

1. Выполни `wk policy sync`.
2. Прочитай `docs/INDEX.md`, `docs/system/overview.md`, `docs/system/domain.md`, `docs/_meta/checklist.md`.
3. Определи затронутые компоненты и прочитай их `docs/components/<компонент>/component.md` и файлы по ссылкам из него. Компонента нет в `docs/components/` — создай его командой `wk component add <имя>`.
4. Пройди `docs/_meta/checklist.md` и выпиши факты, которые задача создаёт или меняет.
5. Для каждой области задачи выполни `wk policy search "<суть>"`. Найденные правила из блока политик в `AGENTS.md` прочитай командой `wk policy show <rule-id>`. Правила вне блока не используй.
6. Заведи или измени каждый факт по `docs/_meta/format.md` и `docs/_meta/ids.md`. Новый факт — статус `draft`. Изменение существующего факта — по разделу 4 `docs/_meta/workflow.md`.
7. В карточке сошлись на применимые политики по ID `rule-…`. Текст правила не пересказывай.
8. Выбор между вариантами оформи `ADR-…` со статусом `proposed` по `docs/decisions/ADR-0000-template.md`. Сценарий через несколько компонентов оформи `FLOW-…` в `docs/system/flows.md`.
9. Факт противоречит правилу уровня MUST — факт не записывай, заведи `Q-…` в `docs/open-questions.md` со ссылкой на правило.
10. Неизвестное значение заведи `Q-…` в `docs/open-questions.md` и сошлись на него из карточки. Догадку в карточку не пиши.
11. В политиках пробел, касающийся всей компании, — вызови скилл `propose-rule` и продолжай по текущим политикам.
12. Код, тесты, миграции и конфигурацию не меняй. Статус `planned` не ставь — его ставит человек.
13. Напечатай для человека список заведённых и изменённых ID и список открытых `Q-…`.
14. Выполни `wk check --strict`.
