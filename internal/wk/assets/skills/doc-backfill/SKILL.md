Вызывать для компонента, у которого код есть, а документации нет или она неполная. Не вызывать для новой функциональности — для неё doc-design. Не вызывать для изменения поведения кода.

# Документирование существующего кода

1. Выполни `wk policy sync`.
2. Прочитай `docs/INDEX.md`, `docs/system/overview.md`, `docs/system/domain.md` и раздел 6 `docs/_meta/workflow.md`.
3. Компонента нет в `docs/components/` — создай его командой `wk component add <имя>`.
4. Прочитай код компонента. Факты, которые выдаёт инструмент (схема БД, зависимости из lock-файлов, OpenAPI, список команд CLI), сверь с выводом инструмента, по памяти не пиши.
5. Заведи карточки и строки таблиц по `docs/_meta/format.md` и `docs/_meta/ids.md` со статусом `implemented`. Объём — по разделу «Бюджет объёма» в `docs/_meta/format.md`.
6. Поставь маркер `doc: <ID>` в каноническом месте по таблице в `docs/_meta/workflow.md`. Кроме маркеров, код не меняй.
7. Для каждой области компонента выполни `wk policy search "<суть>"`. Найденные правила из блока политик в `AGENTS.md` прочитай командой `wk policy show <rule-id>` и сошлись на них в карточках по ID `rule-…`. Текст правила не пересказывай.
8. Код нарушает правило — заведи `RISK-…` в `docs/risks.md` со ссылкой на `rule-…` и на файл. Код не исправляй.
9. Назначение или значение неизвестно — заведи `Q-…` в `docs/open-questions.md`. Догадку в карточку не пиши.
10. Выполни `wk check --strict`.
