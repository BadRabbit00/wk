## Документация проекта

Папка `docs/` — источник правды о проекте. Код пишется по ней.
Если код и документ расходятся, прав документ.

Перед любой задачей:
1. Прочитай `docs/INDEX.md`, `docs/system/overview.md`, `docs/system/domain.md`.
2. Прочитай `docs/components/<компонент>/component.md` того компонента, который затрагивает задача, и иди по ссылкам.
3. Незнакомый ID (`TBL-…`, `API-…`, `DEP-…`) ищи в `docs/_meta/registry.md`.
4. Код открывай только для того, что прямо нужно задаче. Место в коде — `grep -rn "doc: <ID>" .`

Порядок задачи — сначала документация, потом код:
1. Задача меняет поведение, данные, контракты, настройки или зависимости — навык `doc-design`:
   факты в `docs/` со статусом `draft`, ссылки на политики `rule-…`, вопросы `Q-…`. Код в этом ходе не меняется.
2. Человек проверяет документацию и переводит факты в `planned`.
3. Код — навык `implement-planned`, только по фактам `planned`.
4. Код уже есть, а документации нет — навык `doc-backfill`.

Правила:
- Код пишешь только по фактам со статусом `planned` или `implemented`. По `draft` — нельзя.
- Нужно то, чего нет в `docs/` (таблица, поле, эндпоинт, зависимость, переменная окружения)? Остановись
  и предложи изменение документации. Не добавляй это в код молча.
- Не знаешь ответа — добавь вопрос `Q-…` в `docs/open-questions.md`, не выдумывай.
- Реализовал факт — поставь в коде маркер `doc: <ID>` (правила в `docs/_meta/workflow.md`)
  и переведи статус в `implemented`.
- Формат и ID — `docs/_meta/format.md`, `docs/_meta/ids.md`. Не придумывай новые префиксы.
- Инвариант домена — `INV-…`, политика компании — `rule-…`. Это разные вещи.
- В конце работы запусти `wk check` и исправь все ошибки.
- Документация и код меняются в одном коммите.
