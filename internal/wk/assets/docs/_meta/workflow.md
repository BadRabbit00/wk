# Как работать с документацией (для агентов и людей)

Главное правило: **документация — источник правды, код — её реализация.**
Если код и документ расходятся, прав документ, а код — баг. Исключение одно: документ явно
помечен `draft` или ссылается на открытый `Q-…`.

## 1. Как читать

Не читай `docs/` целиком и не начинай с кода.

1. `INDEX.md` — всегда, целиком.
2. `system/overview.md` и `system/domain.md` — всегда.
3. Папка компонента, с которым связана задача: сначала `component.md`, дальше по ссылкам.
4. Встретил незнакомый ID → смотри `_meta/registry.md`: там файл и строка определения,
   места в коде и список тех, кто этот ID использует.
   Без реестра: `grep -rn "^#\+ TBL-orders\b\|^| TBL-orders " docs/`.
5. Код открывай только для того, что прямо нужно задаче. Место в коде ищи по маркеру:
   `grep -rn "doc: TBL-orders" .`

## 2. Как вносить изменения (сначала документ, потом код)

1. **Изменение начинается в документации.** Новая фича, новый эндпоинт, новая колонка —
   сначала карточка или строка в нужном файле со статусом `draft`.
2. Всё, что непонятно, — в `open-questions.md` как `Q-…`, и ссылка на него из карточки.
3. Человек проверяет изменения документации и переводит их в `planned`.
4. **Код пишется только по `planned`.** Код по `draft` писать нельзя.
5. Нужно что-то, чего нет в документации (новая таблица, поле, зависимость, переменная
   окружения) → **остановись** и предложи изменение документа. Не добавляй это молча в код.
6. После реализации: статус → `implemented`, в коде стоит маркер, `wk check` проходит без ошибок.
7. Документ и код — в одном коммите или одном PR.

## 3. Маркеры в коде

Маркер связывает факт из документации с местом в коде. Ставь его **один раз на ID**,
в каноническом месте — там, где факт определён, а не везде, где он используется.

| ID | где ставить маркер |
|---|---|
| API | обработчик / handler эндпоинта |
| EVT | место публикации (у владельца) и обработчик (у потребителя) |
| CLI | определение команды |
| DTO | объявление типа / схемы |
| TBL, KV, BKT | миграция, создающая таблицу, или модель ORM |
| MOD | главный файл модуля (`__init__.py`, `mod.rs`, `index.ts`, `doc.go`) |
| CLS | объявление класса / функции |
| JOB | точка входа задачи |
| CFG | место, где настройка читается |
| PRM | файл промпта или константа с ним |

Синтаксис — обычный комментарий языка, формат один для всех:

```
// doc: API-orders.create            Go, Rust, TS, JS
# doc: TBL-orders                    Python, Nix, YAML, shell, TOML
-- doc: TBL-orders                   SQL-миграции
/* doc: CLS-orders.price-calculator */
```

Несколько ID в одном месте: `// doc: API-orders.create, EVT-order.created`.

## 4. Изменение существующего контракта

- Совместимое изменение (новое необязательное поле) — правим карточку, отмечаем в ней `changed: <дата> <что>`.
- Ломающее изменение — новый ID с версией (`API-orders.create.v2`), старый получает
  `status: deprecated | replaced_by: API-orders.create.v2`, в карточке пишем срок удаления.

## 5. Проверка

```
wk check            # проверка + генерация _meta/registry.md + актуальность политик
wk check --strict   # предупреждения тоже считаются ошибками (для CI)
```

Скрипт ловит:
- дубли ID и ID в неправильном файле;
- ссылки на несуществующие ID и маркеры в коде на несуществующие ID;
- нет статуса / неверный статус / нет владельца;
- `implemented` без маркера в коде и маркер у `draft`/`planned` (статус забыли обновить);
- файлы больше бюджета строк.

## 6. Если проект уже существует (документируем готовый код)

Тот же формат, обратный порядок: агент читает компонент, заводит карточки сразу в статусе
`implemented` и ставит маркеры в код. Всё, в чём он не уверен, — в `Q-…`, а не догадкой в карточку.
Факты, которые можно получить инструментом (схема БД, список зависимостей из lock-файлов,
OpenAPI), сверяются с выводом инструмента, а не пишутся по памяти.
